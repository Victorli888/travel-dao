## Step 0 — Decide the fork first

Everything below is shaped by one unanswered product question, so answer it
before writing the data access layer.

**Today the agent's system prompt says "Notion is the source of truth."**
`runResearchAgent` returns prose; `parseNotionPath` scrapes a URL out of it.
Nothing lands in Postgres. But an itinerary builder needs rows in
`activities` — with a `trip_id`, a `priority_score`, and a placement.

Two destinations for the same research run. Pick one:


| Option                     | What it means                                                                                                                                                                                                       | Cost                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **A — Postgres primary**   | The agent gains a **structured output** step: a tool call (or a final `tool_use` block) returning JSON that conforms to an activity shape, which the route inserts into `activities`. Notion becomes a side effect. | Prompt rewrite, a new zod schema, a write path in the route.           |
| **B — Postgres secondary** | Postgres holds only what the user manually adds and schedules. The agent keeps writing prose to Notion.                                                                                                             | Cheap now. Blocks the wishlist and the rejection-memory feature below. |


**Recommendation: A.** `scratch/where-Iast-left-off.txt` already asks for
"once an activity is scored poorly, save it so it can't be generated again."
That is impossible under B — the agent never produces a row to score.
`CLAUDE.md` also flags that migration `0003` dropped `user_activity_ratings`,
so **nothing currently records rejection**; re-adding that only makes sense
once activities are real rows with stable identity.

Related, and worth deciding at the same time: the **identity key** problem
recorded in `Itinerary-planning.md`. The same real-world place regenerated by
the agent becomes a *new* row with a new uuid. Fixing it needs a normalized
`name + address` key or the `source_metadata` provider id, plus a partial
unique index — not a change to the itinerary tables.

## Step 1 — The data access layer

**This is the actual next commit.** The `Layers` table in `CLAUDE.md` has a
hole: `lib/db/` is described as "schema + client" only. There is no
`lib/itinerary/`.

Without it, a route handler has to write Drizzle calls inline, which breaks
the layering rule already in `CLAUDE.md` — domain data shaping belongs in
`lib/`, not in a route and never in a component.

Think of this layer as the **translation office** between two languages.
Postgres answers a join in flat, namespaced rows
(`{ day_itineraries: {...}, activities: {...} }`). React wants a nested
document (`Day[] → Activity[]`). Every invariant recorded in `CLAUDE.md` —
the double **LEFT JOIN**, `NULLS LAST` on `priority_score`, `NOT EXISTS` for
wishlist items — is a rule that must live in exactly one file, or it gets
re-derived slightly wrong in three.

**Built, but split by entity rather than by read/write.** A `queries.ts` and
a `mutations.ts` would each have grown past 400 lines and every change would
have touched both; four entity files keep a change to activities in the
activities file.

```
lib/itinerary/
  index.ts        the public surface
  types.ts        $inferSelect rows + DTOs
  schemas.ts      zod inputs; pure
  shape.ts        flat rows -> nested document; pure, no DB import
  pg-errors.ts    SQLSTATE -> AppError
  trips.ts        list get create update delete
  days.ts         getItinerary listDays generateDays addDay removeDay
  activities.ts   list wishlist get add update delete
  placements.ts   append place move unplace reorder listPlacements
```

`shape.ts` is separate precisely so the flat-rows → nested-document
transform can be tested without a database — its fixture carries an empty day
and a wishlist item, which are the two cases an INNER JOIN eats.

### Two non-negotiables on line one

- `import "server-only"` at the top of every file in this directory. If a
client component ever transitively imports one, you want a **build error**,
not a bundled `DATABASE_URL`.
- `userEmail` **is a required parameter on every read and every write.**
Drizzle has no concept of **row-level security**. A `where` clause you
forget is a data leak, and because ownership here is an *email string*
rather than a session-bound id, it is unusually easy to forget. Authorize
in the action, filter in the query, both.



### The functions to write

*what are the functions a user need to manage their trip?*

- Create a trip
  - set trip name
  - set start date
  - set end date
  ... etc
- Create a daily itinerary
  - set date
  - append activity
  ... etc
- Add a potential activity
  - set activity description
  - set address
  ... etc

```ts
// reads
listTrips(userEmail): Promise<TripSummary[]>
getTrip(tripId, userEmail): Promise<Trip | null>
getDayItinerary(tripId, userEmail): Promise<Day[]>   // days + placed activities
// listWishlist — proposed, then dropped: no screen needed it, and
// getItinerary derives the unassigned split from rows it already has.

// writes
createTrip(userEmail, { name, startDate, endDate }): Promise<Trip>
generateDays(tripId, userEmail): Promise<Day[]>       // upsert one row per date
addActivity(tripId, userEmail, draft): Promise<Activity>
placeActivityOnDay(dayId, activityId, position?): Promise<void>
unplaceActivity(dayId, activityId): Promise<void>     // returns it to the wishlist
reorderDay(dayId, orderedActivityIds): Promise<void>
setPriority(activityId, userEmail, score: 1|2|3|4|5|null): Promise<void>
```



### Invariants this layer owns

Pulled from `CLAUDE.md` — encode them here once:

- **Both hops are LEFT JOIN.** One so an empty day still comes back, one so a
day with no placements survives. An `INNER JOIN` silently drops every empty
day and every wishlist item, which reads to a user as data loss.
- **No placement row = wishlist item, by design.** Test with `NOT EXISTS`,
never a NULL column. Never filter these out by default.
- `position` **is nullable and means *unordered*, not first.** It lives on the
placement because ordering is a property of the pairing.
- `priority_score` **NULL means unrated, not lowest.** Sort `NULLS LAST`.
- `UNIQUE (trip_id, date)` makes day generation a plain **upsert**
(`onConflictDoNothing`), not a read-then-write.
- `UNIQUE (day_id, activity_id)` blocks the same activity twice on one day.
Surface that as a friendly no-op, not a 500.
- **Cascades are product decisions.** Delete a day → placements go, activities
fall back to the wishlist. Delete a trip → activities are destroyed.
- `numeric` **comes back as a string** (`lat`, `lng`). Parse at the edge; never
add two of them.

## Step 2 — The transaction driver problem

Hit this before writing the first multi-row mutation, not after.

The app uses `drizzle-orm/neon-http`. The **Neon HTTP driver does not
support interactive transactions.** "Create a trip, then generate its nine day
rows" is inherently multi-statement — if it half-fails you get a trip with
four days and no error anywhere.

**Resolved: option 1.** Every mutation is a single statement, and it turned
out to cost nothing:

- `generateDays` reads the trip (a read — nothing is written yet), enumerates
  the dates in TypeScript and issues **one** multi-row
  `INSERT ... ON CONFLICT (trip_id, date) DO NOTHING`. No `generate_series`
  needed, and the upsert makes regeneration idempotent.
- The placement writes are one `INSERT ... SELECT` whose `JOIN` through
  `trips` *is* the authorization check — ownership, same-trip and the write
  in a single statement. Zero rows back means missing, not yours, or a
  different trip, all indistinguishable on purpose.
- `ON CONFLICT ... DO UPDATE` rather than `DO NOTHING` is what makes that
  unambiguous: `DO NOTHING` also returns zero rows for an activity that is
  already placed, which would surface as a spurious `NotFoundError`.

Recorded in `CLAUDE.md`. The original three options, for when this stops
being enough:

1. **Make each write a single statement.** Multi-row
  `insert ... values (...), (...)` plus `onConflictDoNothing`, which
   `UNIQUE (trip_id, date)` already makes safe. This covers day generation and
   bulk activity insert — probably everything v1 needs.
2. **Switch to** `drizzle-orm/neon-serverless` (the **WebSocket** driver) for
  real `db.transaction`. Costs a connection handshake per invocation.
3. **Two clients** — HTTP for reads, WebSocket for the handful of writes that
  genuinely need atomicity. More moving parts; only worth it if measured.

Whichever is chosen, record the reason in `CLAUDE.md` next to the `lib/db/`
row, because the failure mode of getting it wrong is silent partial writes.

## Step 3 — Validation at the boundary

Mirror what `lib/research/schema.ts` already does: **zod** schemas that turn a
bad body into a `ValidationError` (400) rather than a database error (500).

- `CreateTripSchema` — name, optional ISO `startDate`/`endDate`, with a
refinement that end is not before start.
- `ActivityDraftSchema` — the shape the agent must emit under Step 0 option A,
and the shape a manual "add place" form posts. **One schema, two producers**
is the whole point.
- `PriorityScoreSchema` — `z.number().int().min(1).max(5).nullable()`, matching
the `CHECK` constraint so the two can never disagree.

**Built, without `drizzle-zod`** — the schemas are hand-written, which is what
lets the request shape stay narrower than the insert shape (no `id`, no
`user_email`). `schemas.test.ts` is what keeps them from drifting from the
constraints they restate.

Two errors were added to `lib/api/errors.ts` alongside the existing three:
`NotFoundError` (404) and `ConflictError` (409). A missing row and someone
else's row are the *same* 404 on purpose — distinguishing them would leak
which trip ids are real.

`drizzle-zod`'s `createInsertSchema` can derive these from the tables rather
than hand-writing them. Worth evaluating; do not let it generate the
*request* shape, which is narrower than the insert shape (no `id`, no
`user_email` — that comes from the session, never from the client).

## Step 4 — Transport

Three mechanisms, and picking the wrong one is the most common App Router
mistake:


| Need                         | Use                                                   | Why                                                                        |
| ---------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------- |
| Render a trip page           | **Server Component** calling the DAL directly         | No `fetch`, no API route, no loading state, no serialization hop.          |
| Mutate from a form or button | **Server Action** (`"use server"`) + `revalidatePath` | Progressive enhancement, typed args, no hand-written endpoint.             |
| A browser has to POST JSON   | **Route Handler**                                     | Only when something outside React calls it — the way `/api/research` does. |


Concretely: `app/trips/page.tsx` and `app/trips/[id]/page.tsx` are server
components. `app/trips/actions.ts` holds the server actions. **Do not build**
`/api/trips` unless something external needs it.

Session is read with `auth()` inside the action or page, and `session.user.email`
is what gets passed to the DAL. `session.user.isAllowed` is already typed via
`types/next-auth.d.ts`.

## Step 5 — UI

Only now. Existing layering rules apply unchanged: files in `components/ui/`
and feature-view directories may not call `fetch`, may not hold state that
outlives a keystroke, and may not transform domain data.

- `components/itinerary/` — presentational views: `DayColumn`, `ActivityCard`,
`WishlistPanel`, `PriorityStars`.
- One stateful orchestrator per screen, the way `ResearchPanel` is the only one
today.
- Use the `@theme` tokens in `app/globals.css` (`bg-surface`, `border-line`,
`bg-accent`). No hardcoded hexes.
- **Reordering is the hard part.** `position` is nullable, so a drag-and-drop
implementation needs a normalization pass — either renumber the whole day on
every drop (simple, N writes) or use fractional/sparse indexing (fewer
writes, more code). Start with renumber-the-day; it is one statement and a
day holds a handful of rows.

## Known gap this plan does not close

**Nothing ties a placement to a single trip.** `day_itinerary_activities` has
independent FKs, so nothing stops pairing a day from trip A with an activity
from trip B — demonstrated by check 9 in `sql/validate-itinerary.sql`. Closing
it needs a **composite foreign key** carrying `trip_id` on both sides.

Until then it is the DAL's job, which is a weaker guarantee than the database's
and is written down as such in `CLAUDE.md`. `placements.ts` proves it in the
`JOIN`, and `crud.test.ts` covers it: placing a Japan activity on a Korea day
raises `NotFoundError`. Check 9 will keep reporting FINDING regardless — the
database still permits what the layer refuses.
