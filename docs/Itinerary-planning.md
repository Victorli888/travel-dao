> schema *before* migration `0003`: `activities.day_id`,
> `user_activity_ratings` and `trip_destinations` no longer exist. For the
> current model, read `CLAUDE.md` → *Data model*, [architecture.md](architecture.md)

Status: **implemented.** See `lib/db/schema.ts` and `drizzle/0001_*.sql`.

## Entities
- **User** — a user
- **Trip** — a planned journey owned by one user
- **Itinerary** — the daily itinerary for each day of the trip
- **Activity** — something to do; may or may not be scheduled to a day yet

## Relationships
- User 1—N Trip
- Trip 1—N Itinerary
- Itinerary 1—N Activity

## How the sketch mapped onto the real database

The database already held ten hand-built tables when this was written, so
most of the sketch turned out to be already-solved rather than new work.

| Sketch | Reality |
| --- | --- |
| **User** entity, `Trip.owner_id` | No `users` table exists. Ownership is `user_email TEXT REFERENCES allowed_emails(email)`. The allow-list *is* the user table. |
| **Itinerary** | Built as `itinerary_days` — the one genuinely missing entity. |
| `Trip.title` / `description` / `date_range` | Existing `trips` has `name`, `status`, `start_date`, `end_date`. No description column. |
| `Activity.user_rating` | Already `user_activity_ratings.rating`, unique per (user, trip, activity). Not duplicated onto `activities`. |
| `Activity.location` | Already `activities.address` + `lat`/`lng`. |
| `Activity.hours_operation` | Genuinely missing — added as nullable `text`. |
| `Activity.trip_id` | Already present and NOT NULL, cascading from `trips`. |

## Decisions
- Nullable `day_id` rather than separate wishlist/itinerary tables — "add"
  and "schedule" are lifecycle states of one thing, not two entities.
- A day hangs off the **trip**, not off `trip_destinations`. On a multi-city
  trip the city is derived by comparing the day's date against each
  destination's arrive/depart range. Hanging days off destinations would
  force every trip to declare a destination before it could hold any days.
- `UNIQUE (trip_id, date)` — one row per calendar day, enforced by the
  database so day generation is a plain upsert.
- Delete a day → activities return to the wishlist (`ON DELETE SET NULL`).
  Delete a trip → cascade. Both verified against the live database.
- `duration_minutes`/`lat`/`lng`/`position` exist to serve the day-optimizer,
  not the CRUD UI.

## Resolved questions
- **Reordering within a day for v1?** Yes. `activities.position`, a nullable
  integer — cheaper to add before the first migration than after. NULL means
  unordered, not first.
- **Does "look up activities" mean searching my trip, or a wider catalog?**
  Still open, but the schema does not force the choice: `activities` is
  scoped per trip, while `cities` / `countries` / `activity_categories` are
  shared reference data a wider catalog could hang off.

## Known issue, not addressed here
The same real-world place regenerated by the agent becomes a *new*
`activities` row with a new uuid, so it slips past the
`UNIQUE (user_email, trip_id, activity_id)` on `user_activity_ratings` and a
previously rejected place can be suggested again. Fixing it needs an identity
key on `activities` (a normalized name+address, or the `source_metadata`
provider id), not a schema change to the itinerary tables.
